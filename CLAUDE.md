# CLAUDE.md

ScoutSNF: a client-only Vite + React + TypeScript PWA on GitHub Pages doing radius-based
competitive market analysis for skilled nursing facility acquisitions. No backend, no server,
no auth. Deployed live with real users.

## Before you change anything

Every capability in `docs/preservation.md` must survive any refactor as **user-facing behavior**.
The implementation may change freely; the behavior may not.

Read `docs/preservation.md` before touching search, exports, data loading, the map, portfolios,
or Settings. If a change appears to require dropping or altering anything listed there, **stop
and ask** — do not decide on your own.

"Small infrastructure change" is exactly how production features get silently dropped here. A
task framed as "move geocoding into CI" once ended up deleting a Settings control and rewriting
two confirm dialogs. Nothing in the framing warned about it. Assume every task can reach further
than it looks.

Never conclude a listed behavior is dead code because you can't immediately see what calls it.

## Working conventions

- Develop on `claude/pending-edits-c1kbsr`. If that branch's PR was already merged, restart it
  from `origin/main` instead of stacking commits onto merged history.
- Squash-merge PRs.
- **Do not commit or push until I say so.** Show me the diff first.
- Ask before any decision the prompt didn't cover. Don't widen scope on your own initiative.
- **Ask me decisions as interactive questions with clickable options** (the `AskUserQuestion`
  tool), not as prose I have to answer by typing. This applies to the commit/push checkpoint
  above and to any other fork in the road.
- **No new npm dependencies.** Not one, without asking first.
- Verify deploys through the `Deploy to GitHub Pages` Actions run — the live site is unreachable
  from the sandbox. "It built" is not "it's live," and neither is "I merged it."
- Verify by inspecting real output, never by reading config. Grep the built `dist/`, run the
  test, hit the real URL. Config that looks correct is not evidence that it works.
- If I give you a value that must be exact (an ID, key, or URL) and it came from a photo or
  screenshot, **do not use it** — ask me to paste it as text. One misread character has already
  caused a production outage here. Treat your own transcription warnings as stop signs, not
  disclaimers.

## Invariants — do not silently change these

- Facility free-text search matches and ranks by **name, city, and ZIP only**. There is no CCN
  matching and none should be added. Filters (state, kind, bed range, Special Focus status)
  can drive results alone with no text query.
- **Special Focus Facility and SFF Candidate are different populations** and must never be
  collapsed into one flag. Only an SFF is in the program; a candidate is on the watch list.
  Distinct badges, distinct filter options, distinct export labels. See `docs/preservation.md`.
- Radius steps are exactly 10/15/20/25/30/35/40 miles.
- Settings keeps all of: SNF roster date, hospital roster date, hospital bed-data status,
  "Refresh data…", "Re-check facility locations", "Legend — data sources".
- Theme follows the OS preference. `tailwind.config.js` has no `darkMode` key on purpose
  (Tailwind's `media` strategy). Don't add one or introduce a manual toggle.
- Rosters load from static same-origin JSON in `public/data/`. **No geocoding or bulk CMS
  fetching in the browser, ever** — that lives in `scripts/roster/` CI.
- Owner/manager name search stays live and on-demand against CMS (`src/hooks/useOwnerNameSearch.ts`).
- The app works offline via the service worker.
- `src/AccessGate.tsx` wraps the whole app. It's a sign-in log, not security — never "harden" it,
  add a backend, or add an auth library.

## Exports / reports

Any data export or report generated by this app (ScoutBoard, portfolio reports, search results, etc.) must be a styled Excel (.xlsx) workbook — never a plain CSV or raw data dump. Use `src/lib/excelStyle.ts` (shared teal/gold-branded header, zebra rows, wrap text, page setup) as the base:

- Single-table exports: `src/lib/simpleWorkbook.ts` → `buildSimpleWorkbook(...)`
- Multi-sheet reports: see `src/lib/portfolioWorkbook.ts` for the pattern (one sheet per section/facility, shared/overlap sheets highlighted).

Dynamically `import()` these modules at the export call site (not a static top-level import) — `exceljs` is large and must stay out of the main bundle, loading only when an export is actually triggered.

Every export should read as a clean, pretty, presentable report on its own — not just data thrown into rows.

## No disclaimer/explanation captions in the UI

Default to zero muted caption paragraphs under section headers explaining what a section means, how to use a control, or caveating the data (e.g. "Gold-ringed pins are your portfolio's facilities..."). The UI must be self-explanatory through clear labels, structure, and design first — not through prose disclaimers. If a control's meaning isn't obvious from its label/layout, fix the label or layout; don't bolt on an explanation. This applies everywhere, not just one screen.

This is a strong default, not an absolute ban: if a piece of context is genuinely non-obvious and actually necessary (can't be inferred from labels/structure) and isn't already stated elsewhere on screen, it's fine to keep — just make it as unobtrusive as possible (e.g. a `title` hover tooltip on the relevant label rather than a persistent visible sentence) instead of reflexively deleting real information. Don't keep anything that's redundant with something already visible (e.g. a per-row "as of" tag makes a blanket footer saying the same thing redundant — cut the footer). Empty-state messages (e.g. "No saved deals yet") are fine — those aren't disclaimers, they explain an otherwise-blank screen.
